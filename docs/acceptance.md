# Final Acceptance and Verification

The active scope is complete when every criterion below holds and every required command passes. Tactical replanning may derive additional slice checks but may not weaken or replace this contract.

## Run and verify

```bash
make check
make e2e
```

Both exit zero on the completed spine. `make check` covers ruff, pyright, pytest, Biome, tsc, vitest, the production frontend build, and regenerating the frontend API types from the OpenAPI schema with a failure if the committed output differs. `make e2e` builds the frontend, starts the API against a temporary SQLite file, and runs the Playwright smoke test. Their definitions live only in the `Makefile`.

## Ingredients and recipes

- [ ] An ingredient has a name, a free-text unit label, and a current price in cents. Editing the price on the ingredient changes the computed cost of every recipe that uses it.
- [ ] A recipe has a name, a non-negative shelf life in days, ingredient lines with non-negative quantities, and one or more sizes each with a strictly positive portion weight, a non-negative sale price in cents, and a non-negative typical yield count. A size with price zero is accepted. A recipe is rejected if the total typical-yield weight (Σ portion weight × typical yield count across sizes) is zero, since recipe cost cannot be split by weight in that case.
- [ ] The recipe screen shows the computed cost per size from current ingredient prices and typical yield. _Automated check:_ for a recipe costing 200 cents with three sizes of portion weight 50, 20, and 10 and a typical yield of 2 each (typical total weight 160), the API returns per-size costs of 63, 25, and 13 cents; the 62.5/25/12.5 boundary case pins `round_half_up` against Python's banker's-rounding built-in `round()`, which would return 62/25/12.

## Bake

- [ ] Recording a bake requires a recipe, date, and actual count per size, with expiration prefilled as date plus shelf life and editable. The editable expiration must be on or after the baked date; an earlier expiration is rejected. Both dates may be in the past for a historical bake, as long as expires ≥ baked date. _Automated check:_ a bake request with expiration before the baked date returns 422.
- [ ] WHEN a bake is recorded, it creates a `bake` entry, the batch stores total cost and per-size unit cost computed from ingredient prices at that moment and references that entry, and one movement per size with a positive count moves those units from Production to Kitchen; a size with a zero count writes no row. _Automated check:_ `|Σ (unit_cost × count_made) − batch_cost| ≤ ceil(total_units / 2)` cents; a 1010-cent single-size bake of 20 units yields a unit cost of 51; and a 1000-cent bake of three sizes with portion weights 200/100/50 and counts 2/4/2 yields per-size unit costs of 222/111/56 cents, which an equal split by count (125 each) fails (exact equality is not achievable for every yield; see [`data-model.md`](data-model.md)).
- [ ] WHEN an ingredient price changes after a bake, that batch's stored costs are unchanged. _Automated check:_ non-negotiable 2.
- [ ] WHEN all counts are zero, the bake is rejected.
- [ ] Batch cost fields are immutable: no API route updates a batch, and any attempt to change a cost field through any write path is rejected at the database. _Automated check:_ OpenAPI document exposes no PUT or PATCH on the batches resource; the migration creates a `BEFORE UPDATE` trigger on the batch cost columns that raises, and a test issues a raw `UPDATE` of a cost field and asserts it fails. An ORM-only validator is not sufficient because Core and bulk updates bypass it.
- [ ] Undo of a bake follows the same current-balance rule as any entry: it is rejected only if reversing would drive the batch's Kitchen on-hand negative, so units that left and came back do not block it. A voided bake's batch is excluded from stock, batch cost reports, and profit. _Automated check:_ bake, move units out of Kitchen, assert undo is rejected; move them back, assert undo succeeds and stock matches the pre-bake snapshot.

## Locations

- [ ] Kitchen, Sold, Waste, Sampled, and Production exist after migration and cannot be deleted, renamed, or deactivated through the API. _Automated check:_ attempting to rename or deactivate a built-in location is rejected with 422.
- [ ] A user can create, rename, and deactivate a stand or a market. Deactivating a location with units on hand is rejected with the on-hand listed (on-hand must be zero to deactivate). An inactive stand or market rejects new visits and manual moves into it and is hidden as a destination in the visit and manual-move pickers. Moves out of an inactive location remain allowed so stock restored there by undo can be recovered, and a location can be reactivated at any time. There is no API route that deletes any location, built-in or user-created; user locations are deactivate-only. _Automated check:_ OpenAPI document contains no DELETE on the locations resource; ORM relationships from location to movement carry no cascading delete; deactivating a stand or market that holds units on hand returns 422 and the response names the on-hand; a visit at, or a manual move into, an inactive location returns 422; a manual move out of an inactive location succeeds; undo into an inactive location still succeeds when the balance check passes; reactivating a location succeeds.
- [ ] Location create accepts kind `stand` or `market` only; kind is immutable on update. _Automated check:_ a create request naming kind `production`, `kitchen`, `sold`, `waste`, or `sampled` returns 422; an update request attempting to change kind on any location returns 422.

## Ledger, stock, and FIFO

- [ ] There is no API route that updates or deletes a movement or an entry, and no API route that updates or deletes a visit or a batch. Voiding via undo is the only lifecycle change to an entry, and it never removes or edits the original entry's movements. There is no DELETE route for recipes, sizes, or ingredients either: ingredients are deactivate-only (an active flag hides an ingredient from the picker for new recipe lines without affecting the cost of existing lines, see [`data-model.md`](data-model.md)); recipes and sizes have no deactivation concept at all and are simply permanent once created, so restrict-on-reference never applies to them. This no-cascade check covers recipe, size, and ingredient the same as entry, visit, batch, location, and movement. _Automated check:_ OpenAPI document contains no PUT, PATCH, or DELETE on the movements, entries, visits, or batches resources — undo is its own endpoint, not an entry update; a test voids an entry and asserts its original movement rows are unchanged in the database; no ORM relationship among entry, visit, batch, location, movement, recipe, size, and ingredient cascades deletes; the OpenAPI document contains no DELETE on the recipes, sizes, or ingredients resources.
- [ ] On-hand per location, recipe, size, and batch is computed from movements. _Automated check:_ after a sequence of movements, the stock endpoint equals an independent fold over the movement list.
- [ ] Any removal of units from a location takes from the batch with the earliest expiration first and may span batches. Recipe, size, and count are the only batch-selection fields the user provides; a manual move additionally names its source and destination locations. _Automated check:_ two batches of the same recipe and size where the later-baked batch expires first (a legal edited expiration) — removing more than the earlier-expiring batch holds then drains that batch first and takes the remainder from the later-expiring one, so an implementation ordering by baked date or id instead of expiration fails the check.
- [ ] Stock removals are serialized: two concurrent removals whose sum exceeds on-hand cannot both succeed. _Automated check:_ with 10 units on hand, two threads each remove 6 at once; exactly one succeeds, the other is rejected, and stock is never negative.
- [ ] WHEN a removal exceeds on-hand at that location, the whole request is rejected and the response names location, recipe, size, on-hand, and requested. Rejection is atomic: no Entry row and no Movement row is written. _Automated check:_ a rejected manual removal leaves the entry and movement tables unchanged.
- [ ] Saving a visit is one transaction: every constraint for that visit type (non-negativity, counted ≤ on-hand, tossed + pulled ≤ counted, returned + tossed ≤ taken, FIFO availability for every removal) is checked before any movement row is written, and a rejected visit writes no rows at all. A visit's location must be an active stand or market; any other location kind, or an inactive stand or market, is rejected. _Automated check:_ a market visit with `returned + tossed > taken` is rejected and the database has zero Visit, Entry, and Movement rows for that submission, including the Kitchen-to-market `taken` movement; a visit posted against Kitchen, Production, Sold, Waste, Sampled, or an inactive stand/market returns 422. A stand-settlement payload must target kind `stand` and a market-settlement payload kind `market`; posting either against the other kind returns 422.

## Stand visit

- [ ] The form lists every recipe and size currently on hand at the stand with inputs for counted (prefilled to current on-hand, so an untouched row records no sale), tossed, pulled to kitchen, and a separate list of kitchen stock with an input for added to stand, plus cash collected. A (recipe, size) the payload omits is treated the same as an untouched row — counted equal to on-hand, records no sale. These are defaults the user may change.
- [ ] WHEN the visit is saved, units missing since the last visit move to Sold for priced sizes and to Sampled for zero-price sizes, tossed units move to Waste, pulled units move to Kitchen, added units move from Kitchen to the stand, and all movements reference the visit. _Automated check:_ a visit with one priced size and one zero-price size each missing one unit writes a Sold movement for the priced size and a Sampled movement for the zero-price size, and no Sold movement for the zero-price size.
- [ ] WHEN a counted value exceeds on-hand, the visit is rejected with the recipe, size, on-hand, and entered counted value named.
- [ ] WHEN tossed plus pulled exceeds counted for a size, the visit is rejected with that size named.
- [ ] A stand visit has no fee: Pydantic input schemas use `extra='forbid'` project-wide (Pydantic v2 defaults to silently ignoring unknown keys, which would let a stand payload smuggle in a fee), so a stand payload that includes a fee field is rejected outright rather than accepted with the field silently dropped, and the stored `fee_cents` is always 0. _Automated check:_ posting a stand visit with a non-zero fee returns 422; posting a stand visit payload that includes an unrecognized field also returns 422.
- [ ] The saved visit shows expected revenue, cash collected, and shrink (`shrink_cents = expected_revenue_cents − revenue_cents`, positive when short). Expected revenue is computed from size prices at save time and stored on the visit; a later price change never alters a previously saved visit's expected revenue. _Automated check:_ save a visit, change the size's price, reload the visit, and assert expected revenue is unchanged; assert shrink is positive for a visit where revenue is less than expected revenue.

## Market visit

- [ ] The form lists kitchen stock with an input for taken, then for each taken size inputs for returned and tossed. For zero-price (sample) sizes, returned is prefilled to zero and editable, since sample packaging does not survive an event. For priced sizes, returned has no prefill and is required, since assuming it came back would silently inflate expected revenue. These are defaults the user may change. Plus revenue total and fee.
- [ ] WHEN the visit is saved, taken units move from Kitchen to the market, missing units move to Sold or Sampled by the price rule, tossed units to Waste, returned units to Kitchen, and all movements reference the visit.
- [ ] WHEN returned plus tossed exceeds taken for a size, the visit is rejected with that size named.
- [ ] The saved visit shows expected revenue from units sold next to the entered revenue, computed from size prices at save time and stored on the visit as `expected_revenue_cents` so a later price change never alters it. The `expected_revenue_cents − revenue_cents` difference is shown but is not labeled shrink for a market visit.

## Profit

- [ ] Every saved, non-voided visit shows profit equal to revenue minus fee minus the frozen cost of units sold, wasted, and sampled during it, with those three costs on separate lines. _Automated check:_ a fixture that pins per-size `unit_cost` and quantities (not a share of `batch_cost`, which may differ by the bounded remainder), a mixed visit, and an asserted profit in cents equal to revenue − fee − Σ(`unit_cost` × quantity) over the visit's Sold, Waste, and Sampled movements.
- [ ] The home screen lists past entries (bakes, visits, manual operations) with date and location, newest first, visits showing revenue and profit, and each non-voided entry with an undo action. A voided visit is listed as voided with no profit figure and is excluded from any profit or revenue totals.

## Home screen and expiration

- [ ] Stock is shown grouped by inventory location (Kitchen, each stand, each market), then recipe and size, with counts. Production, Sold, Waste, and Sampled are terminal locations and never appear in stock views. Expiration is a per-batch fact: a size row is highlighted when it holds a batch expiring within seven days and flagged distinctly when it holds an already-expired batch; a row holding both carries both markers, broken out by batch, rather than merging the two states. _Automated check:_ after a bake (whose Production-to-Kitchen row exists), a visit, and a toss have put units into Sold, Sampled, and Waste, the stock endpoint returns no group for Production, Sold, Sampled, or Waste; a size row holding one expired batch and one expiring-soon batch reports both states with their per-batch counts.
- [ ] A toss action on kitchen stock takes recipe, size, and count and records Waste by FIFO.
- [ ] Nothing moves to Waste without a user action.

## Corrections

- [ ] Undo targets one original entry (a bake, a visit, or a manual operation) and appends a reversal entry whose movements each carry `reverses_movement`, set to the exact original row's id, in reverse creation order (descending movement id), targeting the same batch as the original movement; the original entry is marked voided. The original movements remain in place. Stock afterward equals stock before the entry. _Automated check:_ stock snapshot before equals snapshot after undo of a full market visit — units taken, some sold, some tossed, some returned — where the reversal of `taken` is checked only after the earlier reversals (sold, tossed, returned) have already restored the market's on-hand, proving the balance check is evaluated sequentially rather than against a single pre-undo snapshot.
- [ ] WHEN a reversal's source is an inventory location (Kitchen, a stand, or a market) and a later movement outside the undo has already consumed that batch there, undo is rejected instead of driving on-hand negative at that source. Reversals whose source is Sold, Waste, or Sampled need no such check. _Automated check:_ a manual move drains a batch after a visit, then undo of that visit is rejected.
- [ ] WHEN an entry is already voided, undo of it is rejected, and a duplicate manual removal cannot be used to bypass that: undoing the same movement row twice is rejected by the uniqueness of `reverses_movement`, not by matching quantity or batch. _Automated check:_ two identical manual removals (same recipe, size, quantity, and resulting batch) produce two distinct movement rows; undoing the first succeeds once and a second undo of that same row is rejected while the second removal's row is untouched.
- [ ] WHEN undo is rejected for any reason, no reversal rows are written and nothing about the original entry changes: a non-voided entry stays unvoided and an already-voided entry stays voided. _Automated check:_ trigger a rejected undo and assert the movement table and the entry's voided flag are both unchanged.
- [ ] A manual movement form moves units between inventory locations, or from an inventory location to Waste, or to Sold or Sampled by the price rule (priced sizes to Sold, zero-price sizes to Sampled), with recipe, size, and count, by FIFO. Its destination may never be a market. Production's only outflow is the bake movement; Sold, Waste, and Sampled receive units from visits and manual removals and lose units only through undo. _Automated check:_ a manual move naming a market as the destination is rejected.
- [ ] A manual operation can be undone with the same rules as a visit: same batch, all or nothing, rejected if already undone. _Automated check:_ toss then undo restores the stock snapshot.

## Login and deployment

- [ ] WHEN not logged in, an unauthenticated request to an application route redirects to login and an unauthenticated request to an API route other than the login endpoint returns 401. The login page and the static asset bundle (the built JS/CSS and other Vite output it needs to render) stay public and are never redirected. FastAPI's default `/docs`, `/redoc`, and `/openapi.json` routes are disabled (`docs_url=None`, `redoc_url=None`, `openapi_url=None`); `make check` regenerates the frontend types from `app.openapi()` in-process, which needs no served route. _Automated check:_ unauthenticated GETs to an application route, an API route, the login page, a built asset, and `/openapi.json` return a redirect to login, 401, 200, 200, and 404 respectively.
- [ ] Logging in with the configured password, compared using a constant-time check (`secrets.compare_digest`), sets a signed session cookie with `HttpOnly`, `SameSite=Strict`, and `Secure` (on by default, disabled only via an explicit local-dev environment variable, never inferred from the request scheme; deployment notes require that variable to be absent in production). A wrong password does not set a cookie; after a bounded number of consecutive login failures from one IP (an in-memory per-IP counter; a maintained library if one fits without a new service, otherwise stdlib), the login endpoint rejects further attempts for a cooldown window. The cookie carries an explicit lifetime (a documented `Max-Age`, e.g. 30 days) and the signed payload carries an expiry claim that the server checks on every request, so a replayed cookie is rejected after the lifetime regardless of client behavior; deployment notes state that rotating the session-cookie-secret environment variable and restarting invalidates every outstanding session, and that after a password compromise the password rotation must include that secret too — login checks the password only when issuing the cookie, so already-issued cookies remain valid for Max-Age if only the password changes. `SameSite=Strict` on this JSON-only API is the CSRF control; no separate CSRF token is required, but every state change, including undo, is a `POST`, and the OpenAPI document declares no state-changing `GET`.
- [ ] The app fails fast at startup if the shared-password or session-cookie-secret environment variable is unset or empty, or if the session-cookie-secret is shorter than a documented minimum of 32 bytes (for example 32 random bytes): it exits non-zero naming the missing or too-short variable, and neither value has a default or fallback in code or in Compose. _Automated check:_ starting the app with either variable unset, then empty, then with the session-cookie-secret set to a value shorter than 32 bytes, exits non-zero instead of serving.
- [ ] With the password and cookie-secret variables provided in a `.env` file that Compose reads (the deployment notes show the lines), and for this local HTTP check the explicit local-dev variable that disables `Secure` cookies also set, `docker compose up` on a clean machine starts one container serving the app on a documented port with the SQLite file on a named volume. The container entrypoint runs `alembic upgrade head` idempotently before starting the server (never `create_all`); a failed migration exits non-zero and the server never starts. The login page loads and an authenticated read endpoint returns 200 against the fresh volume. _Automated check:_ a test migrates an empty database and asserts the five built-in locations exist with their kinds.
- [ ] Deployment notes document the backup command and where the backup goes. Human verification: the user runs the backup command once against the running instance — the local Compose instance from the criterion above is sufficient while the hosting gate is open — and confirms a copy exists.
- [ ] Every screen is usable on a 375 px wide viewport without horizontal scrolling. Human verification: the user opens each screen on a phone.

## Money

- [ ] Every money, weight, and quantity field in the domain, ORM, and API schema is exactly `int`; no field anywhere is `float`, `Decimal`, or a numeric string. _Automated check:_ pyright strict passes; a test enumerates every field the data model lists as money, weight, or quantity — every `_cents` field, plus portion weight, shelf life, movement quantity, and every count or entered-quantity field listed in the criterion below (counted, tossed, pulled, added, taken, returned, count made per size, manual movement count, typical yield count, recipe ingredient-line quantity) — across SQLAlchemy columns, Pydantic fields, and domain dataclass fields (a subclass walk filtered to project modules, since neither SQLAlchemy's mapper registry nor Pydantic's model list sees a plain dataclass), and asserts the exact type is `int` (Integer where applicable); that enumerated list must be updated when a money, weight, or quantity field is added. The same test separately asserts no column, field, or dataclass attribute anywhere is `float` or `Decimal`; a test asserts the OpenAPI document declares every field in that list as `integer`; Pydantic input schemas use strict integer validation, and a test posts `"1"` and `1.5` for one field from each family and asserts 422.
- [ ] Every quantity field (counted, tossed, pulled, added, taken, returned, count made per size, manual movement count, typical yield count, recipe ingredient-line quantity) and every money input field (ingredient price, sale price, fee, revenue) is rejected if negative. Derived money values (profit, the expected-versus-actual cash difference) are signed and may be negative. _Automated check:_ Pydantic schemas declare the input fields with a non-negative constraint; a test posts a negative value for one field from each family and asserts a 422 response; a fixture with fee exceeding revenue asserts a negative profit is returned, not rejected.

## Research and decision gates

- **Hosting target** (VPS with Caddy or an AWS Lightsail instance with an attached block disk; AWS Lightsail Container Service and AWS App Runner are rejected because neither offers a persistent disk for SQLite). Not required for acceptance; the Compose criterion above is sufficient. Must be decided before the first real deployment.

## Deliberately excluded

Per the brief's out-of-scope section: Square API, Found import, ingredient stock, price history, unit conversion, multi-user, editing or deleting history, labor and mileage costing, offline or in-market use. An agent must not count these as required or build adapters for them.
